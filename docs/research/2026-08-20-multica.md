# Multica 当前能力调研

> 调研时间：2026-08-20。优先采用 Multica 官方文档和 `multica-ai/multica` 仓库。未在官方资料中确认的内容，均标为“未确认”。

## 1. Issue 系统模型

### 结论

Multica 已有可直接承载“里程碑 → 薄片票”的两层模型。最合适的映射是：

- **里程碑 = Project**。
- **薄片票 = Project 内的 Issue**。

Project 有目标、说明、状态、优先级、负责人、开始日期、目标日期、资源和自动进度。一个 Project 可包含任意数量的 Issue；一个 Issue 最多属于一个 Project。Project 的说明还会进入该项目下 agent 的执行上下文。这比把里程碑做成普通 Issue 更贴合产品模型。

Project 状态为 `planned`、`in_progress`、`paused`、`completed`、`cancelled`。Project 优先级为 `urgent`、`high`、`medium`、`low`、`none`。项目进度按“`done` 或 `cancelled` 的 Issue 数 ÷ 全部 Issue 数”计算。Project 完成与 Issue 完成相互独立，不会自动互改。

来源：

- https://multica.ai/docs/projects
- https://multica.ai/docs/project-resources

### Issue 字段和层级

Issue 原生支持：

| 能力 | 当前情况 |
|---|---|
| 优先级 | 支持。CLI 可按 `--priority` 筛选。 |
| 标签 | 支持。CLI 有 `issue label list/add/remove`。 |
| 父子关系 | 支持。创建时可传 `--parent`；可用 `issue children` 查询。 |
| 分批执行 | 子 Issue 可设 `stage`（1、2、3……）。最早未完成 stage 全部结束后，会通知父 Issue；父 Issue 的 assignee 是 agent 时会唤醒它决定下一阶段。 |
| 自定义字段 | 支持 text、number、select、multi-select、date、checkbox、URL、actor、multi-actor。 |
| 日期 | 支持开始日期和截止日期。 |
| 依赖关系 | **未找到一等公民的 blocks / blocked-by 依赖字段。未确认有原生 Issue 依赖图。** 可用父子 `stage` 表达批次顺序，或用 custom property 记录依赖，但后者不会自动阻塞执行。 |
| iteration / sprint | **未找到独立的 iteration 或 sprint 对象。** Project 是最接近 milestone 的对象；Issue 的 parent-child + stage 是更细的分解和分批机制。 |

Issue 内置状态为 `backlog`、`todo`、`in_progress`、`in_review`、`done`、`blocked`、`cancelled`。可新增自定义状态，但它必须归入七个固定类别之一。看板列按类别而不是自定义状态生成。

来源：

- https://multica.ai/docs/issues
- https://multica.ai/docs/cli

### 对两层结构的建议

不要额外造一个“Milestone Issue”。直接用：

```text
Project（一次冲刺或一个交付目标）
└── Issue（可独立实现、测试、审查、提交 PR 的薄片）
```

只有一个薄片仍需拆成多批 agent 工作时，才在该 Issue 下使用 sub-issues 和 stage。这样 Project 保持“交付范围”，Issue 保持“可领取工作”，不会多出第三套概念。

## 2. 脚本化接口

### CLI 和 REST API

Multica 的日常表面可脚本化。官方 CLI 支持：

- `multica issue list/get/search/create/update`
- `multica issue assign/status/rerun/cancel-task`
- `multica issue comment list/add/delete/resolve/unresolve`
- `multica issue label ...`、`metadata ...`、`property ...`
- `multica project ...`、`agent ...`、`runtime ...`
- 多数 list 命令支持 `--output json`，官方明确要求脚本解析 JSON，不要解析终端表格。

Personal Access Token（PAT）可直接调用 REST API。请求使用：

```http
Authorization: Bearer mul_...
X-Workspace-ID: <workspace-id>
```

官方示例直接访问 `GET https://api.multica.ai/api/issues`。因此外部脚本可以绕过 UI，用 CLI 或 REST API 读票、改状态、指派和写评论。

来源：

- https://multica.ai/docs/cli
- https://multica.ai/docs/auth-tokens

### “取下一张未分配票”是否原生

**没有找到一个原子的 `claim-next` / `take-next` 命令。** `issue list` 支持按状态、优先级、assignee、project、metadata 筛选，并支持排序、limit、offset；`issue assign` 负责指派并可立即触发运行。因此可以用包装脚本实现：

1. 列出当前 Project 中 `todo` 的 Issue，JSON 输出。
2. 过滤 `assignee == null`。
3. 按优先级和位置选第一张。
4. `multica issue assign MUL-N --to-id <agent-uuid>`。

这不是服务端原子领取。多人同时抢票时可能竞争；单人场景可接受。若以后多人使用，应改成服务端事务或增加冲突重试。

`--sort` 的具体值语法没有在网页参考中展开，官方要求以安装版本的 `multica issue list --help` 为准。当前机器的 Multica CLI 不在 shell `PATH` 中，所以本次没有验证实际 JSON 字段和排序字符串。

来源：https://multica.ai/docs/cli

### daemon 与 server 协议

架构上有两条 WebSocket：用户客户端实时事件，以及 `internal/daemonws/` 的 daemon 唤醒和 RPC。任务领取本身走 daemon API，WebSocket 用于降低延迟，轮询是断线后的兜底。

仓库源码公开，所以协议可以研究；但官方没有发布 OpenAPI / Swagger，也没有把 daemon WebSocket 定义为第三方稳定接口。**不建议外部脚本直接实现 daemon 协议。** 应使用已公开的 CLI 或 REST API；前者还承担版本兼容和认证处理。

来源：

- https://multica.ai/docs/developers/architecture
- https://multica.ai/docs/daemon-runtimes

## 3. daemon 编排细节

### 如何指定 agent CLI 和模型

Multica 的路由单位是 **Agent**：

- Agent 绑定一个 runtime。
- runtime 对应“某台电脑 + 某个 agent CLI”，例如同一电脑上的 `omp`、`pi`、`claude` 会注册为不同 runtime。
- Agent 配置可指定 model、thinking level、instructions、skills、环境变量、CLI 参数、MCP 和并发上限。
- 把 Issue 指派给某个 Agent，就等于选择了它绑定的 CLI、机器、模型和配置。

因此，多 harness 的推荐配置不是每张票临时传 `--runtime omp`，而是建立多个稳定 Agent，例如：

- `OMP Implementer` → `omp` runtime → 指定模型；
- `PI Researcher` → `pi` runtime → 指定模型；
- `Claude Reviewer` → `claude` runtime → 指定模型。

Issue 指派命令只选择 Agent。模型通常是 Agent 级设置，不是 Issue 级参数。切模型可更新 Agent，或为不同模型建立不同 Agent。QwenPaw 和 MiniMax Code 例外：模型由 runtime 自己管理。

Multica 当前官方表列出 24 个工具，其中包含 Pi 和 Oh-My-Pi；README 的营销文字写 23，文档表实际多一项，属于文档计数漂移，不影响 `omp` 已被支持这一事实。

来源：

- https://multica.ai/docs/agents
- https://multica.ai/docs/providers
- https://multica.ai/docs/daemon-runtimes

### 任务分发与回传

指派后，server 创建 Task。daemon 保持持久连接，领取匹配 runtime 的任务，并启动本地 CLI 子进程。任务状态依次可能为：

`deferred → queued → dispatched → waiting_local_directory → running → completed/failed/cancelled`

执行期间，daemon 会把进度、tool call、错误、token 用量和最终结果写回服务器。Agent 可通过注入的、最长 24 小时有效的 task token：

- 读 Issue 字段和评论；
- 写评论；
- 改 Issue 状态；
- 创建 Issue。

Task 完成不等于 Issue 完成。Agent 通常开始工作时写 `in_progress`，交付时写 `in_review`。Task transcript 和执行日志永久关联在 Issue 上。

来源：

- https://multica.ai/docs/tasks
- https://multica.ai/docs/assigning-issues
- https://multica.ai/docs/auth-tokens

### workspace 隔离

Multica 有两类代码资源：

1. **Git repository**：runtime 管理 checkout；普通可克隆仓库默认走 worktree 模式，可并发运行。
2. **Local directory**：可选 `in_place` 或 `worktree`。

`worktree` 模式每个 Task 创建独立 git worktree，位于 runtime 的 workspace 根目录。分支名形如 `agent/<agent>/<task>`。任务结束时，daemon 会把未提交文件也提交到该分支；工作树清理后分支保留。失败任务也保留已有成果。它不会自动合并。

`in_place` 直接改原目录，同一目录默认串行；后续任务进入 `waiting_local_directory`。官方明确把它称为 escape hatch，而不是普通默认值。

需要注意：worktree 是并发隔离，不是安全沙箱。Task 默认拥有运行 daemon 的 OS 用户的全部文件、凭据和网络权限。官方建议用专用 Unix 用户、容器或 VM 建真正边界。

来源：

- https://multica.ai/docs/project-resources
- https://multica.ai/docs/security-model

## 4. Hosted 与自托管

### Multica Cloud 的边界

Cloud 只托管协调面。以下内容存在 Multica 服务器：

- workspace、Project、Issue、评论、状态；
- Agent 配置和 skills；
- Task 状态、运行记录、transcript 和 Agent 回传结果；
- agent `custom_env` 和 MCP 配置。

以下内容留在连接的电脑：

- agent CLI 及其登录凭据；
-代码目录和本地文件；
- 实际命令执行和文件修改。

服务器不会自动上传整个工作目录，但 Agent 主动写入评论或结果的代码片段会进入服务器。

来源：

- https://multica.ai/docs/how-multica-works
- https://multica.ai/docs/daemon-runtimes

### 免费额度与数据位置

官网首页的结构化数据把产品 offer 标为 `0 USD`，且当前 Quickstart 可直接注册使用。Multica 不提供模型；实际模型配额来自用户已登录的 Claude Code、Codex、OMP 等账号。

但官方没有公开 Pricing 页面，也没有在文档中说明 Cloud 的免费 workspace、成员、Task、存储或运行记录额度。**免费额度上限未确认。**

官方资料也没有说明 Cloud 数据中心区域、跨境位置、备份周期或删除后的保留周期。**Cloud 数据所在地和 retention 未确认。** 在正式放入敏感项目资料前，应向 Multica 确认这两项，或改用自托管。

来源：

- https://multica.ai/
- https://multica.ai/docs/cloud-quickstart
- https://multica.ai/docs/providers

### 用户当前大概率使用哪种

本机存在：

- `~/.multica/profiles/desktop-api.multica.ai/`
- `~/multica_workspaces_desktop-api.multica.ai/`

这个 profile 名直接指向 Multica 的 Cloud API 域名，而不是 localhost 或自有域名。因此用户大概率是 **Desktop 客户端 + Multica Cloud 协调面 + 本机 daemon/runtime**。这不是“Desktop 内置完整自托管 server”。

### 自托管最小依赖

最小 Compose 方案需要：

- 服务机：Docker Engine/Desktop、Compose v2、Git、Make、curl、OpenSSL；
- 三个容器：Next.js frontend、Go backend、PostgreSQL 17 + pgvector；
- 执行机：Multica CLI/daemon，以及至少一个已安装并登录的 agent CLI；
- 默认占用本机 3000 和 8080 端口。

自托管替换的是 Cloud 协调面，daemon 和 agent CLI 仍在执行机上。对单人冲刺而言，它增加数据库、升级、备份、登录邮件和公网 TLS 运维。除非数据落地要求明确，当前先用 Cloud 更省时间。

来源：

- https://multica.ai/docs/self-host-quickstart
- https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md

## 5. GitHub 集成方向

### 不是 GitHub Issue 同步

官方 GitHub App 的范围是 Pull Request：

- 根据 Multica Issue 标识自动关联 PR；
- 在 Multica Issue 侧显示 PR 状态、diff 大小、CI 和 mergeability；
- 有 close intent 的 PR 合并后，把 Multica Issue 设为 `done`。

没有 GitHub Issue 导入、单向同步或双向同步的说明。GitHub Issue 与 Multica Issue 是两套对象；当前产品设计明显以 Multica Issue 为工作真相源。

来源：https://multica.ai/docs/github-integration

### 能否自动开 PR

**Multica 的 GitHub 集成本身不能开 PR。** 官方明确说 GitHub App 只读授权仓库，不 push commit、不写评论、不写 status check。Local directory 文档也明确说 Multica 不会自动 push 或开 PR。

Agent 仍然可以在本地运行 `git` 和已登录的 `gh`，自行 push 分支并执行 `gh pr create`。这是 agent CLI 在 daemon 用户权限下完成的动作，不是 Multica GitHub App 的写能力。因此“自动开 PR”必须写进 Agent instructions / skill 的交付契约，并给 daemon 用户配置最小权限的 GitHub 凭据。

建议 PR 使用：

- 分支名包含 `MUL-N`，便于自动关联；
- PR body 写 `Closes MUL-N`、`Fixes MUL-N` 或 `Resolves MUL-N`；
- 合并且没有其他 Open/Draft 工作 PR 后，Multica 自动将 Issue 设为 `done`。

只在分支名或标题写 `MUL-N` 会关联 PR，但不会在 merge 后自动完成 Issue。

来源：

- https://multica.ai/docs/github-integration
- https://multica.ai/docs/project-resources

### 生产可用度判断

**判断：功能上已足够用于单人受控生产工作流，但稳定性应按快速演进的 pre-1.0 产品管理。**

支持这个判断的正面证据：Issue/Project/CLI/API/daemon/worktree/PR 关联/失败重试都已形成闭环；Linux、macOS、Windows 有 Desktop release；发布和修复频率很高。

需要保留的风险：

- pre-1.0 且几乎每日发布，CLI 参数、daemon 行为和数据模型仍可能变；
- 默认无文件系统沙箱，安全边界必须自己建立；
- Cloud 的定价上限、数据区域和 retention 未公开确认；
- GitHub App 是只读观察层，开 PR、push 和 review 仍依赖本机 agent 的 GitHub 凭据与 instructions；
- 高提交量和大量 open items 表明产品仍在快速扩张，不能把“活跃”直接等同于“稳定”。

短期策略：用 Cloud + 本机专用 daemon 用户；固定一个已验证 Desktop/CLI 版本完成冲刺，不在冲刺中每日追新；备份关键 spec 和 Project/Issue 内容。

## 7. 对 workflow v2 的影响

### 新的权威分工

```text
Multica Project       = 里程碑 / 一次冲刺的交付范围
Multica Issue         = 可领取的薄片票（MUL-N）
Multica Task          = 某个 Agent 的一次运行记录
GitHub repository/PR  = 代码、CI、人工 review、merge
本机 daemon + OMP/PI/Claude Code = 实际执行
```

Multica 应成为 Issue、评论、状态、指派和运行记录的唯一真相源。GitHub 不再维护同一批开发票。

### 每天“一条命令领票开工”

Multica 没有原生原子 `claim-next`。workflow v2 应提供一个很薄的包装命令，用户每天只运行：

```bash
workflow next --project <current-project> --agent omp-implementer
```

包装器内部执行：

```text
multica issue list --status todo --project <id> --output json
→ 选 assignee 为空且优先级最高的第一张
→ multica issue assign MUL-N --to-id <agent-uuid>
```

最后一步会创建 Task 并启动该 Agent。若只想占票不启动，则传 `--no-start`；日常“领票开工”不传。

首版不要实现复杂 dispatcher。单人场景的两次 CLI 调用已够。包装器应输出所选 `MUL-N`、标题、Agent、Task 是否入队；没有可领票时明确返回“当前 Project 无可执行票”。实际实现前需用所安装版本的 `multica issue list --help` 固定 `--sort` 值和 JSON schema。

来源：

- https://multica.ai/docs/cli
- https://multica.ai/docs/assigning-issues

### 原设计哪些作废，哪些保留

| 原设计 | v2 处理 |
|---|---|
| GitHub Milestone 管里程碑 | **作废。** 改用 Multica Project。 |
| GitHub Issue 作为薄片票 | **作废。** 改用 Multica Issue（`MUL-N`）。不做双写同步。 |
| `gh issue list` / `gh issue edit` 领票改状态 | **作废。** 改用 `multica issue list/assign/status/comment`，外面只保留一条 `workflow next`。 |
| PR body 写 `Closes #123` 勾 GitHub Issue | **作废。** 改成 `Closes MUL-123`。 |
| 分支名带票号 | **保留并改格式。** 使用 `mul-123-...`，让 Multica 自动关联 PR。 |
| Agent 完成后自动提 PR | **保留为 Agent 交付契约，不归 GitHub App。** Agent 用本机 `gh pr create`；Multica 只读回收 PR 状态。 |
| PR 合并后自动关票 | **保留，改由 Multica 完成。** close intent + 合并 + 无其他 Open/Draft 工作 PR时，Issue 自动 `done`。 |
| 人工最终 review 和 merge | **保留。** `in_review` 是 agent 的交付终点；人决定是否合并。 |

### workflow 总稿应立即改的三点

1. 把所有“GitHub milestone / GitHub issue”改成“Multica Project / Multica Issue”。GitHub 只留 repository、PR、CI、review、merge。
2. 把多 harness 选择写成“指派给预配置 Agent”，不是运行时临时选择 CLI。每个 Agent 固定 runtime、模型和技能组合。
3. 把隔离写成两层：普通 repo 使用每 Task worktree；安全边界使用专用 daemon 用户或容器。不要把 worktree 误写成 sandbox。

最终链路应为：

```text
需求澄清 → spec → 建 Multica Project → 拆 Multica Issues
→ workflow next 领票并指派 Agent
→ daemon 在独立 worktree 运行 OMP/PI/Claude Code
→ Agent 测试、审查、push、gh pr create（Closes MUL-N）
→ Multica Issue 进入 in_review
→ 人在 GitHub review 并 merge
→ Multica 自动 done，Project 进度更新
```
