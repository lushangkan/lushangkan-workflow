# 坏例与改法

## 摘要

全部坏例来自 **2026-07-25 会话 B** 里 GPT-5.6 的真实输出，好例来自同一会话的 Claude Opus 4.8 和注入规范后的 GPT。原始素材见 `docs/analysis/2026-07-25-gpt-vs-claude/`。

- **量化差距**：GPT 全文 50 处引号自造词，Claude 16 处且多为引用真实 artifact 名
- **注入规范后**：GPT 自造词从 23 降到 3，字数少 43%（1.69 万字变 9570 字）
- **编号对应** `SKILL.md` 里的规则编号

## M1 一次只让读者持有 3 项以内

坏（GPT 开头就要读者记住四类概念，第五段才给判断）：

> 你现在真正需要拆的，不是"把 8 个 artifact 分别包装成 8 个 skill"，而是把以下四件目前混在一起的东西解耦：
> 1. 流程编排 2. 模型纪律 3. 状态与产物 4. 存储与工具实现

好（Claude 逐个过筛，每次只持有一项加一个判决）：

> ## 1. proposal — 保留，但砍掉一半内容
> 现在 proposal 的 instruction 塞了：全局写作规则、提案前探索、grilling 触发……
> ## 2. proposal-review — 建议删除为独立 artifact

## C1 用日常词，不造词

| 坏 | 问题 | 好 |
|---|---|---|
| 你现在的体系偏"强治理" | "强治理"要读者解码 | 你现在的流程管得太宽 |
| 编排层很薄，工程纪律可以复用 | 两个自造词 | 调用代码很少，只管顺序；测试和评审这些规矩几个流程能共用 |
| 人手触发：`grill-with-docs` | 没人这么说话 | 手动触发：`grill-with-docs` |
| OpenSpec 只做"变更数据库"，workflow skills 做"执行程序" | 两个比喻都要解码 | OpenSpec 只存变更记录，skills 负责实际执行 |
| 把 OpenSpec 缩回"最小状态骨架" | 自造词 | 让 OpenSpec 只保留 proposal、specs、tasks 三个文件 |

## C3 判断直述，删元话语

坏：

> 我目前最想建议的方向是：保留 OpenSpec 作为"重流程"，另加一条普通任务的轻量路径。

好：

> 建议保留 OpenSpec 走完整流程，另加一条轻量路径给普通任务。

坏：

> 换句话说：OpenSpec 只做"变更数据库"；workflow skills 做"执行程序"。

好：删掉整句。上文已经说过同一件事。

## C4 不用"不是 X，而是 Y"

| 坏 | 好 |
|---|---|
| 这样不是推翻现有体系，而是解决"所有改动都走重流程"的摩擦 | 现有体系不动，只解决所有改动都走重流程的问题 |
| 这里不是把 design 和 tasks 随意糊在一起，而是把它们放进一个有两部分的 artifact | 这个 artifact 分两部分：方案摘要和交付切片 |
| 最危险的不是删掉 OpenSpec，而是同时保留两套半重叠的状态机 | 同时保留两套半重叠的状态机最危险 |

GPT 全文用了 9 次这个句式，Claude 用了 0 次。

## C5 相对词要给参照

| 坏 | 好 |
|---|---|
| 编排层很薄 | 编排层只做路由，不含规则 |
| 当前这套重型 OpenSpec | 当前 OpenSpec 有 8 个 artifact、5 道 gate |
| 一个很薄的 orchestrator | 一个只读状态再调 skill 的 orchestrator |

## C6 抽象名词要落地

坏：

> 每个 skill 只负责一种可复用纪律，不自己吞掉整个生命周期。

好：

> 每个 skill 只管一件事，例如 tdd 只管测试节奏，code-review 只管代码检查。

## C13 命名前过三问

以下三例来自回归测试 E 组（注入正式 SKILL 后的 GPT 输出），由读者标注确认。

坏（给只用一次的概念造名）：

> 固定的 `proposal → ... → apply` 链改成**条件驱动流程**。

好：按修改范围自适应：小修复跳过 specs 和 design，行为变化才要求 specs，架构变化才要求 design。

坏（回避现成术语，组装描述性复合名）：

> 建议把 **OpenSpec 降级为可替换的存储适配器**

好：建议把 OpenSpec 降级为一个 adapter：只负责把变更记录写成文件，可以换成别的实现。

坏（专业概念被过度降级）的背景：C11 阅读难度上限只管句子结构和普通词汇，不要求替换专业术语。adapter、gate、policy 这类词照用，首次出现给一句定义。

## C14 定语最多堆两层

坏（三层定语，英文 tool-agnostic 的生硬翻译）：

> **Change Record** 是工具无关的变更数据接口。

好：

> **Change Record** 是变更数据的接口，不绑定具体工具。

判据来自读者原话："第一眼我不能理解，需要继续细想"。第一眼读不懂就是违规。

## D5 报错给位置、原因、修法
